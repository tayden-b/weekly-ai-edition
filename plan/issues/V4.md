# V4: Archive + /brand + /issues

**Wave:** 2 · **Depends on:** C2, C4

## Context

PLAN §4: `/` is the latest issue; `/issues` is a simple list (not a calendar grid — we are weekly); `/brand` is the brand page (logo, colors, type — supports sharing and the portfolio story).

## Scope

- `/` serves the latest edition (by week id) — the full V1/V2 experience, not a redirect shell (redirect is acceptable; record the choice).
- `/issues`: a simple reverse-chronological list of editions — issue number, date range, the week's headline — hairline-separated rows, no calendar/grid chrome.
- `/brand`: masthead/wordmark, colour tokens with hex values, type specimen (Inter Tight / Inter / Geist Mono in their roles), the take/leave direction from DESIGN §0 — itself designed to the spec (it's a brand artifact).
- Editions discovered from `editions/` on disk at build time — no database.

## Out of scope

- Pagination/search (weekly cadence makes a flat list sufficient — §4).
- The agent-twin routes (T1/T2) linked from these pages — link stubs are fine if T1 hasn't landed; wire through if it has.

## Interfaces

- `editions/<week>.json` on disk (C2 format; use the fixture + a second fabricated edition to prove ordering).
- `@weekly/ui` tokens only.

## Proof

- Preview screenshots: `/`, `/issues` with ≥ 2 editions listed correctly ordered, `/brand`.
- A second edition dropped into `editions/` appears in `/issues` and can become latest — demonstrated.

## Acceptance

- `/` serves the latest edition's full experience.
- `/issues` lists every edition in `editions/` reverse-chronologically — simple list, no calendar.
- `/brand` renders masthead, token swatches with hex, and the type specimen to spec.
- Edition discovery is filesystem-based at build time; adding a file changes the listing.
- `pnpm check` + `pnpm build` green.
