# T2: llms.txt, llms-full.txt, RSS + JSON feeds

**Wave:** 3 · **Depends on:** C2, V1, V2

## Context

PLAN §4: site-wide `/llms.txt`, `/llms-full.txt` (latest issue), `/feed.xml`, `/feed.json`. Feeds are the subscription mechanism at launch (no email — §2). llms.txt follows the llmstxt.org convention.

## Scope

- `/llms.txt` — site map for agents: what the product is, where the twins live (`/{issue}.md`, `/{issue}.json`), links to the latest issue.
- `/llms-full.txt` — the latest issue's full content flattened into one document (all pages + sources list).
- `/feed.xml` (RSS 2.0) + `/feed.json` (JSON Feed) — one entry per edition: issue number, date range, headline, link to `/{issue}`; valid feeds (validate against the specs).
- All generated at build time from `editions/`; referenced from `<link rel="alternate">` on the site + the back page "For agents" block.

## Out of scope

- Per-page feeds, webhooks, email (post-v1).

## Interfaces

- `Edition` from `@weekly/schema`; T1 twins already exist for links.

## Proof

- Feed validation output (W3C feed validator or `feedparser`-style local check) in the PR.
- `/llms.txt` and `/llms-full.txt` pasted excerpts in the PR.

## Acceptance

- `/llms.txt` + `/llms-full.txt` follow the llmstxt convention and cover latest-issue content.
- `/feed.xml` + `/feed.json` are valid feeds with one entry per edition.
- Feed `<link rel="alternate">` tags present in the site head.
- All four artifacts regenerate from `editions/` at build time.
- `pnpm check` + `pnpm build` green.
